# Technical decisions

Short records of the main choices and why they were made.

## 1. Monorepo for frontend and backend
One repository, one README and one CI pipeline make the whole project reviewable in a single place.

## 2. Knowledge in the system prompt, no RAG
The knowledge file is a few thousand words, so it fits comfortably in the model context (sections 1 to 8 go into the prompt, see decision 12). A vector database would add cost and moving parts without improving answers. RAG would be reconsidered if the content grew beyond the context window.

## 3. Groq as primary LLM, Gemini as fallback
Both offer free tiers. The backend routes requests to Groq and fails over to Gemini when Groq is rate-limited or unavailable, so the assistant degrades gracefully instead of failing.

## 4. API keys only in the backend
Every `VITE_` variable is bundled into public JavaScript, so the frontend never holds secrets. The chat endpoint is rate-limited per visitor (an IPv4 address or an IPv6 /56 block) to protect the free-tier quota.

## 5. Static frontend on Cloudflare Workers, backend in Docker on a shared Lightsail instance
The portfolio is static and benefits from a CDN at no cost. It is published as a Cloudflare Workers project with static assets only (no script, so no visit runs code and static requests are free and unlimited), built by Workers Builds from Git on every push to `main`. The backend runs in a container on the AWS Lightsail instance that already hosts the Gedocs demo, behind one shared Caddy that provides automatic HTTPS (decision 20).

## 6. PostgreSQL on Neon
The only stored data is an anonymous log of assistant questions. Neon's free tier is enough, and plain PostgreSQL keeps the project portable. The project is in AWS US East (N. Virginia), the same region as the Lightsail instance, so a query costs a few milliseconds of network.

## 7. The chat log is best effort
The answer is sent first and the log row is written afterwards. If PostgreSQL is down or slow, the visitor still gets an answer and the failure is logged without the question text. The assistant therefore never depends on Neon being available. The cost is that a row can be missing, so a rating may refer to a message that was never stored; the feedback endpoint answers 404 in that case.

## 8. The schema is created from SQL and tracked by Alembic
The database is created once by hand from `backend/sql/schema.sql`, followed by `backend/sql/roles.sql` and `backend/sql/retention_role.sql`, and then marked with `alembic stamp head`. Later changes are Alembic migrations. A test compares the ORM models with `schema.sql`, so the two cannot drift apart unnoticed. The running app connects as a user that can only `INSERT` and `SELECT`; migrations use the owner, and the 90-day cleanup uses its own user, `portfolio_retention` (decision 18). On Neon the roles are created with `CREATE ROLE` in the SQL editor, never from the console, because roles made in the console join `neon_superuser` and could read and write everything.

## 9. No NULL provider, and CHECK constraints instead of ENUM types
Rows where no model was called store `provider = 'none'` instead of NULL, so there is a single way to say it. Statuses and providers are `text` with a `CHECK`: adding a value to a PostgreSQL `ENUM` cannot be undone in a migration, while changing a `CHECK` can. Ids are UUIDs generated by the app, because the browser needs the id of a message before the row is written.

## 10. Groq `gpt-oss-120b` as the main model, Gemini `gemini-3.5-flash-lite` as the fallback
Measured on the free tiers on 2026-10-15. Groq's chat models share a limit of 8,000 tokens per minute, and only the `gpt-oss` models have prompt caching, so Qwen was discarded. Between the two `gpt-oss` models the 120b follows the rules better at the same quota cost. Model names are settings (`GROQ_MODEL`, `GEMINI_MODEL`), not code, because free tiers change often.

## 11. Gemini never serves the EU, the EEA, the UK or Switzerland, and fails closed
Google's terms do not allow the free tier for apps that serve those regions. The country comes from Cloudflare's `CF-IPCountry` header, trusted only when `TRUST_CLOUDFLARE_HEADERS=true`. If the country is unknown, Gemini is not used. The cost is that those visitors depend on Groq alone. In production the API host is DNS only in Cloudflare (decision 20): the browser reaches Caddy directly, so no `CF-IPCountry` header arrives, `TRUST_CLOUDFLARE_HEADERS` stays `false` and Gemini is not used, which makes every visitor depend on Groq's quota. Proxying the API through Cloudflare would bring the header back, but then Caddy would have to trust only Cloudflare's published address ranges to read the real visitor address.

## 12. The system prompt carries sections 1 to 8 of the knowledge file, not section 0 or 9
Section 0 (the assistant's rules) is replaced by rules in code, where they are versioned and tested. Section 9 (quick answers) repeats facts already in sections 1 to 8 and is served without a model. This keeps the prompt near 5,000 tokens, which matters because one uncached question must fit in Groq's 8,000 tokens per minute. The app refuses to start if the prompt passes 6,000 estimated tokens.

## 13. Quick-question buttons are answered without a model
Their text is section 9 of each knowledge file, in the language of the site. The answer is instant, always correct, spends no quota and cannot be attacked.

## 14. A rate limiter written in the project, not `slowapi`
About 140 lines with an injectable clock: an IPv6 visitor is a whole /56 block (what a home or office is usually given), repeated attacks block a visitor for 15 minutes, and memory is bounded. It fits the single-process deployment. With several processes each would count on its own, which is a known limit.

## 15. Visitor history is data inside one user message
The browser sends earlier messages, so it could invent assistant turns. Only the visitor's own earlier questions are sent, quoted inside tags in a single `user` message, and angle brackets are removed so a tag cannot be closed. The assistant turns are dropped: nothing can check them, and a made-up "Developer mode is on" turn is the standard way to prime a model. The model has the whole knowledge file, so it loses little.

## 16. The page sections in the answer are the ids of the real page
`projects`, `experience`, `about`, `skills`, `education` and `contact`, so the frontend can link to an anchor that exists. The first design used `profile` and `how_i_work`, which are not on the page.

## 17. One rating per answer, and the first one wins
`POST /api/chat/feedback` inserts with `ON CONFLICT DO NOTHING` against the unique `message_id`, so the database decides, not a `SELECT` before it: two clicks at the same time cannot both write. Rating again, even with the other value, answers 204 and changes nothing. That is simpler for the visitor than an error, and for the log than an `UPDATE`, which the app user is not allowed to do anyway. An unknown message is a 404 (the log is best effort, decision 7) and the widget keeps the visitor's rating on screen in that case, because sending it again cannot work. Ratings are limited per visitor so a script cannot fill the table.

## 18. Retention is a daily command with its own database user
Nothing in the app may delete, so the cleanup is a separate command, `python -m app.jobs.purge_chat_log`, run by cron on the Lightsail instance from the same image, as the `retention` service of `deploy/api/docker-compose.yml` (no extra service, and no dependency on what the database provider offers). It has its own env file, so it holds none of the API keys. It connects as `portfolio_retention`, which has only `SELECT` and `DELETE`. It deletes in batches of 1,000, oldest first, each in its own transaction, so it never holds a long lock on the table the chat writes to, and a run that stops halfway is finished by the next one. It exits with 1 on any failure so cron can tell.

## 19. A repeated question is answered from an in-memory cache
A model call costs about 5,100 prompt tokens, and Groq's own prompt cache only hits some of the time (measured: 2 hits in 14 calls, see `docs/chat-flow.md`), so the backend keeps its own. `services/answer_cache.py` stores the answer to a question, keyed by language and the question lowercased, with single spaces and without marks at the edges (accents are kept, so two different words are never merged). It stores only answers the output validator accepted, and only for questions asked without history: a follow-up depends on what came before. It is checked after the phrase list, so an attack is still refused and still adds a strike, and before Prompt Guard, because a stored question already passed it. A hit is logged as `answered_cached` with no provider and no tokens (migration `0002`), spends no model budget and still counts against the visitor's rate limit. It lives in the process, for 24 hours and up to 500 entries; that is enough for one API container, and with several each would keep its own copy. The key is a hash of the question after personal data was masked, so the text is not kept; decision 21 explains how the cache now survives a restart. `ANSWER_CACHE_TTL_SECONDS=0` switches it off, and the evaluation set switches it off so it always measures the model. The saving is real but small: free-text questions rarely repeat exactly.

## 20. Shared Lightsail instance behind one Caddy
The Gedocs demo already runs on a 2 GB Lightsail instance, and the API needs about 200 MB, so the API goes on the same instance and the monthly cost does not change. Only one process can listen on ports 80 and 443, so a single Caddy (`deploy/proxy/`) owns them, obtains the certificates and routes each host name to its container over an external Docker network, `web`. Gedocs stops publishing ports and serves plain HTTP on that network; its own Caddy keeps adding its headers. The network has a fixed subnet and Caddy a fixed address, so the API can trust `X-Forwarded-For` only from that address (`FORWARDED_ALLOW_IPS`). The Caddy has no `trusted_proxies`, so it ignores any forwarded address a visitor sends and writes the real one; that is what stops a visitor from faking an address to get around the rate limit. The API host is DNS only in Cloudflare for the same reason.

How a change reaches production: a push to `main` that touches `backend/` or `deploy/` runs the tests, builds the image in GitHub Actions and publishes it to GHCR; the server never builds. The deploy step connects over SSH with a key that can run only `deploy/scripts/deploy.sh` (forced command), which pulls the repository and the image and replaces the container. Migrations are not part of it: they are run by hand from a developer machine, so the Neon owner URL never lives on the server. The frontend is built and published by Cloudflare Workers Builds from the same branch.

Alternatives: a second instance (cost, and a second thing to patch); running the API behind Gedocs' own Caddy (couples two projects that should deploy independently); a Cloudflare Tunnel (no public ports, but another dependency and the visitor address would come from Cloudflare); a platform with scale to zero (cold starts on the one endpoint that must answer in seconds).

Limits: one uvicorn process, because the rate limits live in memory and the state file (decision 21) has a single writer; 2 GB shared with Gedocs, whose nightly reset peaks at about 700 MB, so each container has a memory limit (API 384 MB, retention job 256 MB, Caddy 128 MB); and a short interruption of the Gedocs demo during the first switch to the shared proxy. `docs/deploy.md` is the runbook.

## 21. Persisted chat state in a volume file
Each deploy restarted the process and with it threw away two things worth keeping: the answer cache, and the count of tokens spent today, which handed the Groq free quota (about 200,000 tokens a day) back to zero on every release. The same change added a per-visitor limit on questions that reach a model (3 an hour and 6 a day, `ModelQuota`) and made the daily budget count tokens instead of calls, because the quota is in tokens (a call costs about 5,400, so the old limit of 300 calls never matched the real one of about 37).

What persists, and what does not. `services/state_store.py` writes one JSON file (`STATE_FILE`, `/data/state.json` in the `api_state` volume) with the cache entries and today's token count. The cache key is the sha256 of the normalized question, so a visitor's text is never kept in memory or on disk; only validated answers, whose content comes from the knowledge, are stored. The per-visitor counters are not saved: that would mean writing addresses to disk, and the privacy rule of the log (no IP) applies to every file. So a deploy resets each visitor's allowance, which is an accepted limit.

How. A task saves every 30 seconds if something changed, and the shutdown does a final save (the deploy waits up to 45 s). The write goes to `state.json.tmp` and is renamed, so a crash never leaves half a file. The file carries a version and a fingerprint of the system prompt: if the knowledge, rules or canary changed, the cache is dropped and the budget is kept. The saved day must be the current UTC day. A missing, corrupt or unwritable file only logs a warning; the chat never depends on it, as with the database log. The setting is `None` by default, so development and tests keep everything in memory.

Alternatives. Neon: the app role can only `INSERT` and `SELECT` (the log is append-only by design), and the chat must not depend on the database. Redis: a new service on a 2 GB instance shared with Gedocs, for one process and about 1 MB of data. A bind mount: the named volume copies the image's owner on first mount, so no manual `chown` on the server.

Limits: one process and one writer (decision 20); at most 30 seconds of changes are lost if the process dies; `docker compose down` keeps the volume, only `docker volume rm` empties it (see `docs/deploy.md`).
